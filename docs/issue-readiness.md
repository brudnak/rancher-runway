# Issue readiness

**Is this issue ready to test?** runs a read-only evidence check from the issue itself. The action is available on Issue Radar cards, My Work issues, linked Test Package bucket entries, and the open package overview.

Runway reads the issue state and milestone, the single-select **Status** value on accessible GitHub Projects, pull requests that close the issue, pull requests referenced in the issue timeline or body, and pull request links written in comments. A ProjectV2 or issue-discussion access problem is reported as an incomplete scan. Discovered PR references are labeled as closing links, cross-references, or mentions so a reviewer can distinguish GitHub's explicit closing relation from text that may need confirmation.

For merged closing PRs and explicit issue declarations in PR descriptions, Runway checks moving Rancher head tags across its configured image registries and checks both `rancher/rancher` and `rancher/rancher-agent`. It compares each merged fix with the observed server and agent revisions and reports registries and tags where all applicable fixes are included together. When the issue has a release milestone, the report calls out its release line and whether a matching head build is ready. It checks the milestone’s release line and default `head` first. The default head’s release is verified from image metadata or the source revision’s `RancherVersionDev`, not assumed from today’s version. **Search other release heads** offers broader discovery; scans without an identifiable target also use broader discovery.

An open or unmerged PR remains in progress; a closed PR without a merge does not count as a fix. PRs found only in discussion are shown for review and do not establish readiness on their own. An explicit `Issue <URL>` or closing declaration in a linked PR description can identify a required fix; quoted examples and code samples do not count. A successful result requires complete issue-link discovery and evidence for every applicable closing PR in both images. Missing registry data, inaccessible issue links, or truncated scans remain unknown and are called out in the report.

The scan uses the existing GitHub CLI sign-in and the image checker’s registry access. It does not change issues, project fields, pull requests, images, labels, assignments, or workflows. Image tags are mutable observations; review the reported digest, commit comparison, and target environment before testing.

## QA template found on GitHub

The report detects **QA Testing** templates in the issue description and paginated comments, including root cause, what changed, areas to test, regression areas, and reproduction steps. It links to the source and previews the detected sections. Blank templates are labeled **needs details**. Quoted examples and fenced Markdown templates do not count. Detection is structural, not an assessment of the guidance’s quality. A found template does not mean test cases have been saved in Runway.

Comments, closing links, cross-references, and project status are fetched independently. Missing project permissions therefore do not discard accessible comments or PRs. Incomplete comment pagination produces an unresolved QA result rather than asserting that no template exists. The scan checks up to 1,000 items per connection and 30 PRs; reaching either limit is reported explicitly.

## Build evidence

Community `head` / `vX.Y-head` and Prime `vX.Y.Z-head` selectors are filtered before the result limit, so immutable build tags cannot crowd out the moving heads. Each candidate must contain all required fixes in both its server and agent images. Evidence from different registries or tags is never combined into a single ready result.

An explicit, single-original backport declaration in a discovered PR can identify an alternative integration commit for the same fix. Unrelated PRs remain separate requirements. Ambiguous backport prose or declarations naming multiple originals are not used to collapse fixes. A default-branch fix without an identified backport still needs ancestry evidence in a release head. Unknown branches and dependency-repository fixes are not silently excluded. For Steve, Runway reads `go.mod` at each observed Rancher image’s exact source commit, honors module replacements, resolves the pinned version to a Steve commit, and checks the PR merge’s ancestry. For webhook, it reads that Rancher commit’s `build.yaml` (including supported image environment defaults), resolves the chart branch to a commit, verifies the pinned chart and image defaults, inspects the webhook image, and checks its source ancestry. The report links the pin, chart, and comparisons, and records the webhook digest. Webhook proof applies to the server-selected component; the Rancher agent does not embed it. Cluster-level webhook overrides can differ from these defaults. Missing pins, older source layouts without `build.yaml`, unsupported forks, and unavailable provenance remain unknown. A merge upstream alone is never sufficient.

Unavailable registries can coexist with an available, proven build. Incomplete issue-link discovery or failed PR lookups prevent an overall ready result. Workflow status, GitHub QA guidance, and local test preparation remain separate from build inclusion. Closing the dialog aborts its request, and a later response cannot replace a different issue’s report.

## Daily My Work briefing

Enable **Settings → Daily issue readiness → Scan My Work automatically each day** to scan the saved My Work scope on the first app open or return to focus each local calendar day. It is off by default and persisted in the workspace. A newly pulled scope can run that day as well. The scan refreshes the milestone from GitHub without creating packages or changing package placement; it updates the saved My Work issue snapshot. **Scan now** is available even with automatic scanning off.

My Work keeps the latest report with its exact scope, observation time, per-issue workflow states, proven server/agent build pairs, GitHub QA template links, and issues without locally saved test cases. Counts exclude closed issues and issues labeled **QA/None**, including labels discovered during a scan. Test-case coverage uses the most recently updated package for each issue, matching My Work’s existing behavior. Reports describe the saved scan, not live counts after later edits.

A daily job observes mutable images once and shares that observation across the issues in that job. It checks at most 100 open issues, with a 20-minute overall bound and a four-minute per-issue bound. Completed observations are saved incrementally in the private `.daily-readiness.json` file alongside the test-package library. Unchecked, incomplete, cancelled, failed, and interrupted work remains visible. Restarting does not repeat that day’s attempted scan; use **Scan now** to retry. Turning off the setting cancels an active automatic scan. Scans require the local Runway server to remain open; this is not an external scheduler.

Manual and daily scans show an elapsed timer, spinner, current activity, and expandable recent steps. Missing QA templates and blank templates are highlighted as actions needed; an incomplete comment scan remains unresolved. **QA/None** issues return immediately with a clear “QA not required” result.

## Workflow and the green light

Workflow status is highlighted near the top of each report and in the daily briefing. **Green light to test** requires an open issue, a complete workflow lookup showing **To Test** or **QA Working**, and proven inclusion of every required fix in a matching Rancher build. Hyphenated status names and `status/` labels are normalized. In Progress, In Review, Blocked, conflicting project statuses, unset fields, and unavailable status access remain cautionary even when a build is available. Closed issues and QA/None never receive a green light. QA template guidance remains a separate check.

GitHub Projects requires the CLI token’s `read:project` scope. When GitHub rejects that scope, Runway displays the reason and `gh auth refresh -h github.com -s read:project` as a manual recovery step. Complete GitHub authorization, then check again. Runway does not modify credentials or project status. Build availability stays visible independently; older saved daily reports require a new scan to establish combined workflow readiness.
